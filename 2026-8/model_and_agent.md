# 从 Claude Code 到 OpenCode：当内网有了 DeepSeek，我如何重塑 AI 编程工作流

这里使用gemini辅助编写博客

## 一、 开发环境介绍

聊工具选型前，必须先交代开发环境——**内外网严格隔离的双轨开发体系**：

* **内部开发网络（核心代码驻留地）**：出于某些原因，业务源码与底层代码严禁离开内网。网络内完全无法调用外部公网 API，所有推理必须收敛于公司私有化集群部署的模型。
* **外部办公网络（自由探索区）**：可以自由访问公网，第一时间体验最新的公网商业模型与前沿开源社区方案。

---

## 二、 初始阶段

在终端自治 Agent 普及之前，内网的 AI 辅助编程整体处于初级阶段。

### 1. 外部主流生态 vs 内网真实处境

* **外部参照系**：公网环境下，Cursor 和 VS Code 的 GitHub Copilot 凭借单文件行级补全（Autocomplete）和侧边栏 Chat 成为标配。
* **内网真实处境**：依赖云端认证与公网 API 的插件完全无法在内网运行，日常只能依赖私有化部署的Qwen模型提供的网页端。
* **外网探索**：在外网机上通过 ChatGPT 网页端（或者类似的工具），搜索引擎进行疑难排查和算法推演。

这套模式下，**开发者本质上是“上下文搬运工”**：手动脱敏代码切片、复制终端报错贴进网页框，再人肉比对 Diff、手工改回工程代码，缺乏端到端验证闭环。

### 2. 过渡期的插件自救与挫败

之后开始在曾在 VS Code 中配置通用开源插件，将请求代理转发给内网模型。但在面对真实的大型工程项目时，该方案迅速碰壁：

* **行级补全水土不服**：补全对时延极其敏感（通常需 <200ms）。内网私有化部署的通用模型在并发调度与推理加速上缺乏针对性优化，频繁出现格式错乱与复读。
* **超大工程击穿脆弱上下文**：核心仓库代码量庞大、模块调用链路深。单文件切片无法理解全局依赖，而一旦强行塞入多个头文件与实现，内网早期模型有限的有效长上下文便瞬间被击穿，引发严重的注意力稀释。


## 三、Claude Code + Kimi 时代的算子调优探索

随着 Claude Code 展现出惊人的终端自治与自闭环调试能力，开始在外部尝试后之后，发现了借助ccr作为转发接入claude code，开始尝试“借壳”：**将 Claude Code 的底座路由代理至内网私有化部署的 Kimi 2.6（后升级至 Kimi 2.7）**。在外部的万络环境。试着用claude code的模型后老是被封号后，就转发到deepseek的方案。

当时开发的一个任务是**基于 Agent 进行 NPU 底层高性能算子开发**。这套拼装方案在落地中暴露了严重的协议与上下文冲突。

### 1. 协议错配与“上下文问题”

* **工具调用（Tool Calling）频繁唤起失败**：Claude Code 的脚手架高度深度契合其原生模型。内网 Kimi 在解析其复杂的 Tool Call 格式时频频报错，当时比较困扰我的一个问题是写入文件经常失败，导致我需要手动编写一个写skill来实现功能。


* **算子领域知识与上下文膨胀**：底座模型缺乏私有 NPU 硬件细节先验，必须外挂大量私有 API 手册与规范，导致有效上下文极速消耗。

* **人工充当 Context GC**：为了维持会话，只能在各模块维护 `CLAUDE.md` 与局部知识库强制收敛行为；把任务切成极细粒度的微任务；频繁手动重置会话并提炼 Summary 喂给新对话。

### 2. 基于 Skill 链与 Markdown 状态中继

为了降低上下文负载，设计了一套**基于 Markdown 中继的轻量 Skill 链**：每个 Skill 专注单一职责，执行完后将结构化结论固化为 `.md` 文档，下一个 Skill 直接读取该文档作为输入。

```
[算子源码 + NPU硬件知识库]
          │
          ▼
┌──────────────────┐
│ Skill 1: 瓶颈分析 │ ──► 生成 roofline_analysis.md (Roofline 边界 / 理论访存极限)
└──────────────────┘
          │
          ▼
┌──────────────────┐
│ Skill 2: 空间提取 │ ──► 生成 search_space.md (可变参数 / Kernel 搜索空间)
└──────────────────┘
          │
          ▼
┌──────────────────┐
│   人工校验修正    │ ──► 修正非法硬件对齐与寄存器溢出风险
└──────────────────┘
          │
          ▼
┌──────────────────┐
│ Skill 3: 循环调优 │ ──► 编译运行 -> 抓取 Profiling (Cycle/带宽) -> 最优决策
└──────────────────┘

```

* **Skill 1（瓶颈分析）**：输入算子逻辑与 NPU 硬件参数切片，推导计算访存比，输出 `roofline_analysis.md` 明确性能瓶颈边界。
* **Skill 2（搜索空间提取）**：逆向提取 Tile Size、流水线深度、双缓冲分配等超参数，生成类似 TVM 的调优空间 `search_space.md`。
* **人工介入（Human-in-the-Loop）**：人工审核并修正候选参数，剔除可能引发硬件 Bank 冲突或寄存器溢出（Register Spill）的非法配置。
* **Skill 3（AI 版 TVM 自动调优闭环）**：Agent 将候选参数注入模板，调用交叉编译工具链推送到 NPU 运行，抓取 Cycle 周期数、Vector/Cube 利用率和带宽饱和度等 Profiling 数据，因果归因后输出 `best_kernel_config.md`。

实际上这个工作做得也是跌跌转转，很大程度上，底座模型的不行，经常出现同一套流程跑下来，混乱不堪，不能保证一致的情况。

后续这个工作交给其他同事。

## 四、 范式进化：DeepSeek V4 Flash + OpenCode 的全面重构

尽管 Skill 链跑通了流程，但 Claude Code 的闭源黑盒属性导致协议转换 Overhead 极高。随后，因为公司内部要求，全部切换到opencode．然后伴随着模型逐步升级，继续开发。然后就是七月底的DeepSeek V4 Flash。公司的ai模型维护部门很快就上线了这个模型。我很快就发现这套模型性能非常好。

## 五、 实战落地：跨网络、多 Agent 隔离协同的九步研发流

这个过程就是一开始也是边摸索边开发，一遍写代码一遍写。也在看一些新的方法论。

基于 Graph Engineering 与经典软件工程规范，结合内网实际环境，构建了一套跨网络、双模型、多 Agent 隔离协同的九步研发流水线。

### 核心心法：上下文强隔离与“审阅分离”

**严禁同一个 Agent 既当运动员又当裁判员。** 

模型在同一上下文内对自身生成的代码具有强烈的证实偏见。架构设计、代码审查必须在独立的全新上下文（Clean Context）中交由独立 Agent 进行对抗式审校。

```
[外网办公网]                     [内部开发网]
  GLM-5.3 / Kimi 3.0              DeepSeek V4 Flash / GLM-2.7
        │                                     │
 1. 外部竞品与方案调研                          │
        │ (.md 方案草案)                       │
        └───────────────────────────────► 2. 扫描内网仓库拓扑与历史资产
                                              │
                                         3. 制定概要设计与详细设计
                                              │
                                         4. 独立 Agent 评审 (Clean Context) ◄──┐
                                              │                                │
                                         5. 审阅意见回传设计 Agent ────────────┘
                                              │
                                         6. 人工核心裁决 Sign-off
                                              │
                                         7. 任务拆解：业务实现与测试用例解耦
                                              │
                                         8. Agent A 编码 ──► 独立 Agent B Review
                                              │
                                         9. 自动化编译与测试自闭环

```

### 九步端到端落地流程

1. **外网宏观对标**：在外网利用公网前沿模型（GLM-5.3、Kimi 3.0）分析开源社区同类项目与前沿方案，提炼架构草案。
2. **内网现状扫描**：将草案转入内网，由 DeepSeek V4 Flash 扫描本地代码库目录与接口定义，分析现有模块依赖与技术债务。
3. **架构方案设计**：主设计 Agent 编写模块的概要设计与详细设计文档（输出为结构化 Markdown）。
4. **独立 Agent 评审**：启动一个**无历史上下文**的 Review Agent，仅注入当前设计文档与必要接口切片，审查边界条件与异常处理。
5. **设计闭环自愈**：将 Review 意见传回原设计 Agent，进行针对性的设计修订。
6. **人工关键裁决（Human-in-the-Loop）**：开发者介入把关，审查确认最终版详细设计与架构红线。
7. **任务解耦与拆分**：将详细设计拆解为颗粒度明确的任务书，**将业务逻辑实现与测试用例开发彻底解耦**。
8. **编码与交叉互审**：
* Agent A 依据任务书编写业务实现；
* 独立的 Agent B 在干净上下文中进行 Code Review，排查内存泄漏、边界越界与风格对齐。


9. **编译构建与自愈测试**：制定编译与单测脚本，在 OpenCode 终端中运行测试，捕获报错日志驱动 Agent 自主 Debug，直至测试全绿。

## 六、 协作介质与演进方向

目前在整个流程中，多 Agent 间的数据流转与状态同步主要依赖最可靠的“三大件”：**Git 分支与 Commit、Markdown 状态中继、以及人工适度中转**。

* **现状**：纯文本 Markdown 和 Git 提供了天然的工程断点与上下文硬隔离，保证了内网受限模型不会因多轮交互而产生注意力稀释。
* **未来演进**：随着 **DeepSeek-Harness** 等开源插件生态在多 Agent 通信与状态路由方向的完善，后续将逐步引入自动化的 Agent 间通信管道，在 OpenCode 内部实现从“手工中继”到“全自动图编排（Graph Engineering）”的流水线跃迁。

从迷信闭源 Agent 的“开箱即用”，到构建“**开源高质底座 + 开放可控 Harness + 严密工程图编排**”，不仅彻底解决了内网数据隔离与适配问题，也让 AI 辅助开发真正深入到底层系统的生产落地中。

## 我的想法

作为一个科班出身,我最近越来越觉得本科期间上的很多课都蛮有意义的.比如软件工程,软件测试,编译器.实际上很多情况对于我而言,这些课程和最大的意义可能只是记得一个名词,然后再编程的时候想起来,去知乎或者ai搜索看看。然后用起来，真的是奇妙的感觉。

最近的Graph Engineering也好，本身也可以看成是软件工程在ai时代的新的演进。当然随着模型的进步，我上面的知识很大概率会变成无效知识。
